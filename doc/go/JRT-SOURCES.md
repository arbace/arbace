# jrt's translated input

B1a step 3 ([B1-PLAN.md](B1-PLAN.md)), first part: the plain Java of the translation closure
measured in [JAVA-SURFACE.md](JAVA-SURFACE.md) (decision 2: all of it translated from jdk26u's
source with j2c, only the VM's edge hand-written), turned into class forms reproducibly, checked
against javac, and the edge the translated code calls into listed for jrt and c2g.
Measured on the branch `jrt-sources` (from main at `95658ce`, 2026-10-08), JDK 26.0.2.1 built
from `/root/jdk26u` (openjdk/jdk26u at `baf63fb`), its boot JDK 25.0.4.

Summary: **184 Java files** (176 of `src/java.base/share/classes`, 8 generated by the JDK
build's tools, regenerated here byte-identical to the JDK build's) **convert with j2c and
compile from their class forms to javac's class shapes, all 184 (591 classes)**,
deterministically, in about 90 seconds. The translated classes, whole files, call outside
themselves into **188 classes, 678 members**: 51 shimmed classes (310 members), 9 reworked (30),
1 for c2g (2), 47 cut (179), and 80 classes that are plain Java but outside the closure's files
(157). Every one of the closure's 342 boundary members is accounted for. Three bugs were found
and fixed on the way (j2c's printer, the class forms compiler's NaN constants, the shape
comparison of float constants).

## The tool

`bin/jrt-convert [--twice]` (bash) with its Clojure in `test/g2c/jrt_sources.clj`
(`g2c.jrt-sources`, next to `g2c.java-surface`, whose class reading and treatments it reuses).
It runs on Arbace's `target/stage2` (`bin/build-arbace` first) and writes only under
`.tmp/jrt/` (`JRT_WORK`), regenerated on every run and not tracked (the user's decision for
j2c's output). Steps (`JRT_STEPS`, default all):

| step | what | output |
|---|---|---|
| sources | the closure's files: the keys of `[:closure :repl :sources]` in `doc/go/java-surface.edn` (`SURFACE`; `bin/java-surface F` recomputes it), copied from `$JDK/src/java.base/share/classes` | `src/java.base/`, `sources.txt` |
| generate | the 8 generated files, made as the JDK build makes them (below) and compared byte for byte with the JDK build's `support/gensrc` when `$JDK/build` has one | `src/java.base/`, `generated.edn` |
| convert | `bin/j2c -m arbace.j2c.main jdk --check conv java.base src/java.base`: attributed as `java.base` with `--patch-module` against the running JDK (built from the same sources), run from `.tmp/jrt` so its patch directories stay there | `conv/` (184 class-form files and 17 package files, 70,146 lines) |
| javac | the same tree compiled twice by javac with `java.base`'s build options (`-XDstringConcat=inline`, `--patch-module`, `-implicit:none`, as `bin/j2c-check --jdk`) | `ref1/`, `ref2/` (591 classes) |
| check | `bin/class-forms-check` on chunks of about 8 files, `JRT_JOBS` JVMs (default 4, `-Xmx3g` each), `REF=ref1:ref2` (classes javac made from a file that the forms did not make count as differences), the compiled classes written out | `res/`, `forms-classes/` |
| edge | `g2c.jrt-sources/write-edge` on the forms' classes, and on javac's for a cross-check (the two must be the same) | `edge.edn`, `edge-javac.edn` |
| report | the counts and the edge's tables; a hash of every file of `src/`, `conv/`, `forms-classes/` | `report.md`, `report.edn`, `manifest.sha256` |

`--twice` then makes the sources, runs the generators and j2c a second time into
`.tmp/jrt/again/` and requires identical trees. Exit status 0 when all 184 files convert and
compile to javac's shapes (and, with `--twice`, deterministically). Environment: `JDK`
(default `/root/jdk26u`), `SURFACE`, `GEN_JDK` (below), `JRT_WORK`, `JRT_JOBS`, `J2C_JVM_OPTS`
(default here `-Xmx8g`). Peak memory: one 8 GB j2c JVM, then four 3 GB check JVMs.

The release build passes no `-d` (`DEBUG_OPTION` only for debug builds with absolute paths).
`bin/jrt-convert` compiles the two tool packages with `GEN_JDK`'s javac (11 files, about a
second) and runs them with `GEN_JDK`'s java and the build's `JAVA_SMALL` flags
(`-Duser.language=en -Duser.country=US -XX:+UseSerialGC -Xms32M -Xmx512M
-XX:TieredStopAtLevel=1`), about 3 seconds for the 8 files.

**The generator JDK matters.** The JDK build runs its tools on the boot JDK (`JAVA_CMD` of
`build/*/spec.gmk`: `/usr/lib/jvm/java-25-openjdk`), and `GenerateCaseFolding` filters the
regex entries with the *running* JDK's `Character.toUpperCase`/`toLowerCase`. Run on JDK 26
(Unicode 17) it leaves out 28 entries for characters new in Unicode 17 (`A7CE`..`A7D5`,
`16EA0`..`16EBF`, ...) that JDK 25 (Unicode 16) does not know and so keeps; the JDK we run was
built with them. `GEN_JDK` therefore defaults to the boot JDK read from the build's `spec.gmk`
(else `/usr/lib/jvm/java-25-openjdk`), and with it **all 8 files are byte-identical to the JDK
build's** (`build/linux-x86_64-server-release/support/gensrc/java.base`). The other 7 do not
depend on the generator JDK. (The dependence is the JDK build's own quirk: its `CaseFolding`
changes with the boot JDK's Unicode version.)

### Fixed on the way

1. **j2c's printer took time exponential in nesting depth.** `pp-call` lays out a call's
   arguments aligned, then again indented when that is too wide, so a deep chain of calls
   doubles the work per level. The generated `CharacterData*` tables are string concatenations
   of hundreds of lines (nested `+`), and their conversion did not finish in 10 minutes. `pp`
   is now memoized per form (by identity) and column within `form-text`
   (`arbace/j2c/print.clj`, `*pp-cache*`); the 8 generated files convert in 14 s, and the
   output is unchanged (the 176 other files converted with and without the change: identical
   trees; `bin/j2c-check` passes).
2. **The class forms compiler wrote NaN constants with the sign bit set.** `Double.NaN` is
   `0.0d / 0.0`, which the analyzer folds; on x86 the division gives `0xfff8000000000000`, and
   ASM writes a constant's raw bits, where javac writes `doubleToLongBits` (the canonical
   `0x7ff8000000000000`). `Double.NaN` and `Float.NaN` came out with the wrong bits
   (observable through `doubleToRawLongBits`). `arbace/classes/emit.clj` now writes float and
   double constants (`ldc` and `ConstantValue`) with the canonical NaN, as javac does.
3. **The shape comparison could not see it.** `arbace/classes/shape.clj` compared a field's
   constant with `=`, and NaN is not `=` to itself: javac's own two runs of `Double` and
   `Float` "differed", so both classes were set aside as javac's nondeterminism (these are
   likely the 2 classes that `bin/j2c-check --jdk` does not compare, CONVERTER-NOTES.md, "The
   converted JDK"). Float and double constants are now compared by their bits as well as their
   printed value, in fields and in code.

After 2 and 3 (and `bin/build-arbace`, which still reproduces itself byte for byte), Double
and Float are compared and identical; `bin/j2c-check` and `bin/class-forms-tests` pass.

## The edge (for c2g and jrt)

The edge is read from the classes compiled from the forms (and, identically, from javac's):
every reference to a class outside the 591 translated classes, a member resolved as the JVM
resolves it (a call on a translated class that it inherits from `Object` or `Throwable` is
`Object`'s or `Throwable`'s; a constructor is always its own class's), with the top-level
translated classes that use it. It covers **whole files**, as c2g will translate them, where
the closure's boundary (JAVA-SURFACE.md) covers only the methods reached from Arbace's uses;
the full data is in `.tmp/jrt/edge.edn`, the tables in `.tmp/jrt/report.md`.

Two options of the conversion (amendment S2):

- **`J2C_PATCH_ALL`** (an environment variable of j2c's `jdk` conversion,
  `arbace/j2c/main.clj`; `bin/jrt-convert` sets it): each chunk of packages has the other
  chunks' sources on its patch path, its own first. jrt's own Java in `jdk.internal.jrt` is used
  across packages (`java.io`), and with more files the chunks split it apart (javac: "package
  jdk.internal.jrt does not exist"). Opt-in, so `bin/j2c-check --jdk` is unchanged.
- **`known-differences`** (`g2c.jrt-sources`): files whose classes differ from javac's in known,
  harmless ways, by file with the kind and the number of differences, count as converted when
  the number matches (any other difference fails): a lambda constructing a local class passes
  the class's captured variables in capture order, javac in reverse (`Collectors` 3,
  `Gatherers` 9, `MatchOps` 12), and an `InnerClasses` entry javac's stack map frames name
  (`Nodes` 2).
